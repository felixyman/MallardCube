The model file `proxy-config.json` describes the cube. It maps tables and
columns in DuckDB to the dimensions, measures, and roles that Excel sees. It is
the only file a project requires.

Here is a working model for a small sales database:

```jsonc
{
  "catalog": "SALES_ANALYTICS",
  "cube": "Sales",
  "table_name": "sales_fact",
  "dialect": "duckdb",
  "db_path": "sales.db",

  "dimensions": [
    {
      "id": "Category",
      "physical_field": "category",
      "caption": "Category",
      "hierarchy_name": "Category",
      "all_level_name": "(All)",
      "leaf_level_name": "Category",
      "ordinal": 1,
      "visible": true,
      "has_all": true,
      "cardinality_hint": 50
    }
  ],

  "measures": [
    {
      "id": "Revenue",
      "sql_expr": "SUM(revenue)",
      "caption": "Revenue",
      "display_name": "Revenue (USD)",
      "format_string": "#,##0.00",
      "ordinal": 1,
      "visible": true,
      "measure_group_name": "Sales"
    }
  ]
}
```

## Formats, defaults, and large models

The config can be JSON or YAML (detected by extension, then by content). YAML
suits large hand-maintained models: comments, readable non-ASCII, clean diffs.

Only `id` and `caption` are required per dimension and measure — captions
cascade to hierarchy/leaf names and display names, `ordinal` follows list
order, `all_level_name` defaults to `(All)`, `visible` to true,
`physical_field` to the id, `format_string` to `#,##0.00`, and a measure's
`measure_group_name` follows its fact table (or the cube).

Split large models into section files; inline entries come first and paths
resolve relative to the config:

```yaml
dimensions_file: dimensions.yaml
measures_file: measures.yaml
roles_file: roles.yaml
```

`mallard fmt` canonicalizes a config and converts between formats:

```bash
mallard fmt my-project/proxy-config.yaml
mallard fmt --check my-project/proxy-config.yaml
mallard fmt --to yaml my-project/proxy-config.json
```

A rewrite does not preserve YAML comments.

## Top-level fields

| Field | Purpose |
|---|---|
| `catalog` | Name Excel shows as the database. Used in the ODC `Initial Catalog`. |
| `cube` | Name Excel shows as the cube. |
| `table_name` | The fact table in DuckDB. |
| `dialect` | Set to `"duckdb"`. |
| `db_path` | Path to the DuckDB file, relative to the config file. Omit to use the bundled sample data. |
| `dimensions` | Array of dimension definitions. |
| `measures` | Array of measure definitions. |
| `relationships` | Optional. Joins between fact columns and dimension tables. |
| `roles` | Optional. Security roles (see [Security and roles](./security/)). |
| `auth` | Optional. Authentication mode (see [Security and roles](./security/)). |
| `fact_tables` | Optional. Multiple fact tables. |
| `time_intelligence` | Optional. Date dimension metadata for time functions. |

## Dimensions

A dimension is a column or table that groups rows. The minimal dimension is a
single column on the fact table, as in the example above.

Fields:

| Field | Purpose |
|---|---|
| `id` | Internal identifier, unique, no spaces. Used in logs and caching. |
| `physical_field` | The column this dimension reads. |
| `caption` | Label shown in Excel. |
| `hierarchy_name` | Hierarchy name in XMLA. Usually the same as the caption. |
| `all_level_name` | Label of the "(All)" member. |
| `leaf_level_name` | Label of the leaf level. |
| `ordinal` | Sort order in the field list. |
| `visible` | Whether Excel shows the dimension. |
| `has_all` | Whether an "(All)" member exists. |
| `cardinality_hint` | Approximate member count. Shown in metadata. |

### Dimensions from a separate table

When the dimension lives in its own table, add a relationship and a
`physical_field` that names the dimension column. The `Date` dimension below is
an example: the fact table stores `date_key`, and the levels come from
`date_dim`.

### Multi-level hierarchies

A dimension with levels supports drilldown. Levels are listed in `hierarchy_levels`,
coarsest first:

```jsonc
{
  "id": "Date",
  "physical_field": "full_date",
  "caption": "Date",
  "hierarchy_name": "Date",
  "all_level_name": "(All)",
  "leaf_level_name": "Date",
  "ordinal": 5,
  "visible": true,
  "has_all": true,
  "cardinality_hint": 5000,
  "is_date_role": true,
  "hierarchy_levels": [
    { "name": "Year",    "column": "year",    "level_number": 0, "cardinality": 11 },
    { "name": "Quarter", "column": "quarter", "level_number": 1, "cardinality": 44 },
    { "name": "Month",   "column": "month",   "level_number": 2, "cardinality": 132 },
    { "name": "Date",    "column": "full_date", "level_number": 3, "cardinality": 4018 }
  ]
}
```

Each level names the column in the dimension table that holds that level's
value. `is_date_role: true` marks this dimension as the calendar used by
time-intelligence measures.

### Parent-child hierarchies

A dimension table that stores a self-referencing key/parent pair — an org
chart, a chart of accounts — uses `parent_child` instead of
`hierarchy_levels`:

```jsonc
{
  "id": "Employee",
  "physical_field": "employee_key",
  "caption": "Employee",
  "hierarchy_name": "Employee",
  "all_level_name": "(All)",
  "leaf_level_name": "Employee",
  "ordinal": 6,
  "visible": true,
  "has_all": true,
  "parent_child": {
    "key_column": "employee_key",
    "parent_column": "manager_key"
  }
}
```

The dimension needs a relationship to its own table, the same way a date
dimension does. On the serving path MallardCube materializes the recursion
into `{dimension_id}__pc_l1..N` columns with synthetic levels (`Level 01`,
`Level 02`, ...), then serves compound unique names and subtree rollups like
any other hierarchy. `qualify` and `trace-replay` reuse an existing
materialization and never write to the database. After the source data
changes, set `"refresh": true` to rebuild the levels on the next start (or
drop the `__pc_*` columns).

## Measures

A measure is an aggregation over the fact table.

| Field | Purpose |
|---|---|
| `id` | Internal identifier, unique. |
| `sql_expr` | DuckDB expression, for example `SUM(revenue)` or `SUM(units)`. |
| `caption` | Name shown in Excel. |
| `display_name` | Optional longer label. |
| `format_string` | Excel number format, for example `#,##0.00`. |
| `ordinal` | Sort order in the measures list. |
| `visible` | Whether Excel shows the measure. |
| `measure_group_name` | Group label. Usually the fact table name. |

`sql_expr` is the only runtime. There is no DAX or measure formula language:
each measure is a SQL aggregate expression that DuckDB evaluates.

### Time-intelligence measures

A measure can filter by a date flag column for year-to-date or similar
semantics:

```jsonc
{
  "id": "RevenueYTD",
  "sql_expr": "SUM(revenue)",
  "caption": "Revenue YTD",
  "format_string": "#,##0.00",
  "ordinal": 3,
  "visible": true,
  "measure_group_name": "Sales",
  "time_intelligence": {
    "dimension_id": "Date",
    "flag_column": "ytd_flag"
  }
}
```

`flag_column` is a boolean column in the date dimension table. The query adds a
filter that keeps only rows whose flag is true. The `date_dim` table generated
by AutoModel ships with `ytd_flag`, `qtd_flag`, `mtd_flag`, and
`prior_year_ytd_flag` columns.

## Relationships

A relationship joins a fact column to a dimension table column:

```jsonc
{
  "relationships": [
    {
      "fact_table": "default",
      "fact_column": "date_key",
      "dimension_id": "Date",
      "dim_table": "date_dim",
      "dim_column": "date_key"
    }
  ]
}
```

`fact_table` is `"default"` for the single-fact case. The join becomes
`sales_fact.date_key = date_dim.date_key` at query time.

## Date dimension metadata

The `time_intelligence` block tells the proxy which columns make up the date
dimension:

```jsonc
{
  "time_intelligence": {
    "date_dimension": {
      "dimension_id": "Date",
      "table_name": "date_dim",
      "date_key_column": "date_key",
      "full_date_column": "full_date",
      "flag_columns": {
        "year_column": "year",
        "quarter_column": "quarter",
        "month_column": "month",
        "ytd_flag_column": "ytd_flag",
        "qtd_flag_column": "qtd_flag",
        "mtd_flag_column": "mtd_flag"
      }
    }
  }
}
```

This block is required for time-intelligence measures and for date drilldown.

A dimension marked `is_date_role: true` with `hierarchy_levels` also exposes its
leaf level as a single-level **key attribute hierarchy**, named after that level
(`[Date].[Full Date]` beside the user hierarchy `[Date].[Calendar]`). That
hierarchy carries the date data type, which is what makes Excel offer
**Date Filters** (equals / is before / is after / between, plus the calendar
picker) on the date field. The field list shows both hierarchies; drag either.

## Multiple fact tables

For models with more than one fact table, list them in `fact_tables` and scope
each dimension and measure with a `fact_table` field. See the `projects/project4/`
sample for a two-fact model.
