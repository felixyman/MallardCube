---
title: Aggregations
description: Rollup tables for large fact tables
---

Every measure query MallardCube runs is an aggregation over the fact table.
On a large fact table, a year drilldown still reads every row to compute a
dozen values. The aggregation layer pre-computes rollup tables so those
queries read a few thousand rows instead.

## Enable

Set `MALLARDCUBE_AGG_CACHE` to the path of a sidecar database:

```bash
MALLARDCUBE_AGG_CACHE=/var/cache/mallardcube/agg.duckdb \
  PROXY_CONFIG=/path/to/proxy-config.json \
  cargo run
```

On startup the server builds rollup tables into the sidecar, then attaches it
read-only. The sidecar is a separate DuckDB file. MallardCube never writes to
your database.

## What gets rolled up

For each multi-level dimension in the model, MallardCube builds one rollup per
level. The sample `Date` dimension has Year, Quarter, and Month levels, so it
produces:

| Table | Grain |
|---|---|
| `agg_year` | year, plus each leaf dimension |
| `agg_quarter` | year, quarter, plus each leaf dimension |
| `agg_month` | year, quarter, month, plus each leaf dimension |

Each rollup stores the pre-summed measures at that grain. A year drilldown then
reads `agg_year` instead of scanning the fact table.

## When a rollup is used

A query uses a rollup when all of these hold:

- The measure is an additive `SUM`.
- The query groups at the rollup's grain or coarser.
- Every filter is on a column the rollup contains.
- Every active row-level-security predicate can be evaluated on the rollup
  (see below).

Everything else reads the fact table as usual. Queries for time-intelligence
measures or leaf-level drilldown fall back to the fact.

### Row-level security

Rollups are built from the full fact, so a role predicate must be *applied* to
the rollup query — never ignored. MallardCube rewrites each predicate onto the
rollup when every column it references is carried there with the same values:

- flat dimension values (e.g. `territory = 'North'`, `f.territory = 'North'`);
- date level columns the rollup stores (e.g. `_date.year = 2024` on the year
  rollup);
- expressions over those columns (e.g. `RIGHT(territory, 3) = 'rth'`).

If any reference cannot be mapped — a fact column that was not rolled up, a
deeper date level than the rollup stores, another table/alias, a quoted
identifier, or a subquery — the query keeps the fact path. Correctness over
speed: a rollup must never bypass row-level security.

## How it stays correct

Rollups are rebuilt when the source changes. The sidecar stores a stamp of the
source file size and modified time, and skips the rebuild when the stamp
matches. After every build, MallardCube checks that each rollup sums to the
same total as the fact table. A mismatch discards the rollups and the server
continues on the fact path.

To force a rebuild, delete the sidecar file.

## Limitations

- Only `SUM` measures use rollups. `COUNT`, `MIN`, `MAX`, and expressions do not.
- A role predicate that cannot be evaluated on the rollup (see above) keeps
  the fact path for that user.
- The build scans the fact table once at startup. On a very large table the
  first start takes minutes while the rollups are built (the bench notes in
  `docs/SCALING.md` have numbers).
