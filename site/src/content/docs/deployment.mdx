MallardCube is a single binary with no runtime dependencies. The two things to
sort out for production are the reverse proxy and the data directory.

## Reverse proxy

:::caution[Secure by default]
MallardCube refuses to start on a non-loopback address unless an auth mechanism is
configured (`auth.trusted_proxy` or `auth.oidc`). Without auth every client that can
reach the port is an administrator; if that is genuinely what you want (an isolated
lab, say), set `MALLARDCUBE_ALLOW_ANONYMOUS=1` and accept the warning.
:::

Put an authenticating reverse proxy in front of the server. The proxy
terminates TLS and handles authentication, then forwards to the local bind
address.

```nginx
server {
    listen 443 ssl;
    server_name cube.example.com;

    # TLS certificate configuration here.

    location /xmla {
        proxy_pass http://127.0.0.1:8080;

        # Overwrite the header from the authenticated identity. Never forward a
        # client-supplied header, or a client could claim any user name.
        proxy_set_header X-User $remote_user;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

Run the server bound to localhost only:

```bash
BIND_ADDRESS=127.0.0.1:8080 cargo run
```

TLS terminates at the proxy. MallardCube itself does not handle TLS.

## Docker

Published images are on GitHub Container Registry:

```bash
docker run -p 8080:8080 ghcr.io/felixyman/mallardcube:latest
```

To build the image yourself, a `Dockerfile` is in the repository root:

```bash
docker build -t mallardcube .
docker run -p 8080:8080 mallardcube
```

The image includes the bundled sample project, so it serves the demo without a
config. To serve your own model, mount a config directory:

```bash
docker run -p 8080:8080 \
  -e PROXY_CONFIG=/config/proxy-config.json \
  -v "$(pwd)/config:/config" \
  mallardcube
```

A `docker-compose.yml` is included. It serves the bundled sample project out
of the box (`docker compose up --build`); for your own model, pass
`PROXY_CONFIG` and mount the project directory, as shown in the comments in
that file. DuckDB is statically linked, so the runtime image has no shared
library requirements.

## Refreshing data

MallardCube keeps a pool of read-only connections open for the life of the
process, and DuckDB allows one writer or many readers on a file — never both.
So a load job cannot run while the server does, the server cannot start while
a load job holds the file, and the server keeps serving the snapshot it opened
until it restarts.

1. Build the new data into a staging file (`build.duckdb`) while the server
   keeps serving.
2. Rename it over the live file: `mv build.duckdb live.duckdb`.
3. Reload in place (`kill -HUP <pid>` / `systemctl reload mallard`) or restart
   the service. A reload clears the result cache and falls back to the fact
   table if aggregation rollups became stale; a restart rebuilds them.

Where signals are awkward, set `MALLARDCUBE_RELOAD_WATCH=<secs>` and the server
polls the file's size+mtime, reloading when it changes.

## Monitoring

`GET /health` answers `200 ok` for liveness probes. `GET /status` reports the
served file, its size and mtime, and when it was loaded:

```bash
curl -s http://localhost:8080/status
```

Both endpoints are auth-gated when `auth` is configured (trusted header or
bearer token), and both expose no table data.

## Prebuilt binaries

Releases publish binaries for Linux x86_64, macOS arm64, and Windows x86_64.
Download the binary for your platform from the GitHub releases page and run it
directly; there are no runtime dependencies.

## Logs

MallardCube writes to standard output and standard error. Set `MALLARDCUBE_DEBUG=1`
to add a verbose request log at `debug-last-run.log`. Set `XMLA_TRACE=1` to
record every request and response as NDJSON, which the `trace-replay` and
`load-replay` commands can play back.

## Performance

A query's cost is a full scan of the fact table, so scale is mostly about
storage and memory:

- Enable [aggregations](../aggregations/) for coarse pivots on large fact tables.
- Keep the DuckDB file on fast local storage.
- Set `MALLARDCUBE_POOL_SIZE` if you want a different number of connections
  than the CPU count.
- Excel repeats each pivot query once per `CELL PROPERTIES` variant; the
  built-in 5-second result cache collapses those repeats into one execution.
  Disable it with `MALLARDCUBE_RESULT_CACHE=0` if you need zero staleness, and
  bound its memory with `MALLARDCUBE_CACHE_MAX_BYTES` (default 64 MiB; `0`
  keeps only the entry cap). `/status` reports entries, bytes and hit rate.

The repository ships a benchmark harness in `scripts/bench.sh` that generates a
large Parquet fact table and measures latency and throughput against a live
server.
