# Plan 040: YAML configuration and git-friendly config handling

## Status

- **Priority**: P2 (developer/adopter experience; complements Gate G1)
- **Effort**: M
- **Risk**: LOW (additive format support; JSON paths stay untouched)
- **Depends on**: none
- **Category**: DX / configuration

## Why this matters

`proxy-config.json` is the model definition users read, review, and tweak by
hand. As JSON it is hostile to exactly that:

- No comments, so the non-obvious fields (`fallback_capability`,
  `filter_expression` aliases, `parent_child.refresh`, `is_date_role`) cannot
  explain themselves in place.
- SQL expressions are single escaped strings; multi-line fallback SQL is
  unreadable.
- Diffs churn: adding one measure reflows a brace-delimited object, and a
  trailing-comma mistake is a parse error.
- Reviewers cannot see *why* a filter or a stub exists.

YAML fixes all four (comments, block scalars, line-oriented diffs, schema-driven
editor support). The audience that hand-edits configs — contributors, demo
authors, and adopters adjusting converter output — benefits immediately, and
the converter/AutoModel keep generating files either way.

## Design

### Format support (dual, sniffed)

YAML is added as a first-class input/output format; **JSON remains supported
and remains the converter's default output** so existing projects, fixtures,
scripts, and CI do not change.

New module `src/project/config_io.rs`:

```rust
pub enum ConfigFormat { Json, Yaml }

/// Sniff by extension first (*.yaml/*.yml), then by content
/// (first non-whitespace char '{' => JSON, else YAML).
pub fn detect_format(path: &Path) -> ConfigFormat;

pub fn parse_config(text: &str, path: &Path) -> Result<ProxyConfig, String>;

/// Canonical serialization: declaration-order fields, block scalars for
/// multi-line strings, deterministic output.
pub fn write_config(config: &ProxyConfig, format: ConfigFormat) -> Result<String, String>;
```

- Crate: `yaml_serde = "0.10"` (the YAML organization's maintained fork of
  `serde_yaml`; `serde_yaml` is archived and `serde_yml` is deprecated with
  RUSTSEC-2025-0068). API is `serde_yaml`-shaped (`from_str`/`to_string`).
- Parse errors must carry the config path plus the YAML error's line/column,
  and be returned as `Err(String)` (never a panic) so startup and tools report
  a clean message.
- Verify boolean handling: `yaml_serde` follows YAML 1.2 core schema, so
  `caption: NO` stays the string `"NO"` (the Norway problem). Add a regression
  test. Generated strings are quoted to be safe.

### Wiring

- `ProxyProject::load` (and therefore `qualify`, `trace_replay`,
  `init_project`) uses `parse_config`. No new entry point.
- `resolve_db_path` is unchanged (path-based, format-agnostic).
- Converter (`convert-tabular`) and AutoModel (`auto-model`) gain
  `--format json|yaml` (default `json`). With YAML they write
  `proxy-config.yaml` next to the existing output; bootstrap assets are
  unaffected.
- `main.rs` config loading path is unchanged apart from the parser.

### Canonical output (git-friendly)

- Field order is the struct declaration order; review `ProxyConfig` and pick a
  readable canonical order (suggested: `catalog`, `cube`, `db_path`,
  `dialect`, `source_name`/`table_name`, `dimensions`, `measures`,
  `relationships`, `fact_tables`, `time_intelligence`, `roles`, `auth`) — the
  same order is used for JSON and YAML output.
- All strings are quoted on write; multi-line strings use literal block
  scalars (`|-`/`|`), so `sql_expr` and fallback SQL stay readable.
- Generated YAML starts with a header:
  ```yaml
  # yaml-language-server: $schema=./proxy-config.schema.json
  # Generated by mallard <subcommand> — edit freely; regeneration overwrites.
  ```
- The writer is one-way: hand-edited files are never rewritten (comments
  survive), which is what makes YAML worthwhile for review.

### `mallard fmt [--check]`

Parse + canonical write (YAML only). `--check` exits non-zero when the file is
not canonical, for CI/pre-commit. This removes whitespace churn as a review
distraction and gives contributors a single obvious formatting command.

### JSON Schema

Ship `proxy-config.schema.json` at the repo root (hand-authored from the serde
types; asserted complete by a test that walks the field list). Used by editors
for both formats (`$schema` key / language-server comment).

### Sample project

Add `projects/project2/proxy-config.yaml` as the YAML twin of its JSON config
and a test asserting both parse to the same `SemanticConfig`. Keep every other
sample in JSON to bound churn; the YAML twin doubles as a template for
hand-authoring.

### Docs

- README: "Project structure / config" section documents both formats, the
  YAML template, and `mallard fmt`.
- `docs/DEVELOPER-GUIDE.md` appendix: add the YAML mapping notes (block
  scalars, quoting rules).
- New `docs/configuration.md`: YAML-first reference with annotated examples,
  including a role with `filter_expression` comments and a multi-line fallback
  measure. Link it from README and the docs site (`site/`).

## Out of scope (follow-ups)

- **Derivable-field defaults** (`hierarchy_name` ← caption, `all_level_name` ←
  "(All)", `visible`/`has_all` ← true, `ordinal` ← declaration order,
  `cardinality_hint` ← auto-detect). Recommended as the next config plan; YAML
  plus defaults is the combination that makes hand-authoring pleasant.
- Config includes / split files for very large models.
- TOML support.
- DAX→SQL lowering for `dax_filter` (tracked under the Phase 4 candidates).

## Test plan

- Unit `config_io`: same project parsed from JSON and YAML yields equal
  configs; format sniffing by extension and by content; multi-line `sql_expr`
  round-trips through YAML; `caption: NO` parses as a string; malformed YAML
  reports path + line; malformed JSON reports path.
- CLI: `qualify <yaml-config>` on the project2 twin returns the same verdict
  as the JSON config; `convert-tabular --format yaml` output parses back;
  `auto-model --format yaml` output parses back; `mallard fmt --check` exits
  0 for canonical YAML and 1 after hand-whitespace damage.
- Schema: test asserts every `ProxyConfig`/`DimensionConfig`/`MeasureConfig`
  serde field appears in `proxy-config.schema.json`.
- Existing JSON tests must pass unchanged (no fixture churn).
